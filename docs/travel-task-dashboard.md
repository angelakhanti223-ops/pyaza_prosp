# Вылеты, прилеты и задачи

Внутренняя страница `/crm/operations`, пункт меню «Вылеты и задачи». Доступна авторизованным сотрудникам с той же видимостью заявок и задач, что на существующей доске CRM. В публичный каталог страниц и аналитику посетителей не входит.

## Работа на странице

- Период: сегодня, 7 или 30 дней, с выбором начальной даты. Даты и сроки отображаются по Москве.
- Вылеты и возвращения за период, ответственный, ссылка на заявку и связанные открытые задачи.
- Общая очередь задач: требуют внимания (сегодня и просроченные без повторов), просроченные, сегодня, в периоде, выдача документов, без срока, все открытые.
- Фильтр ответственного и кнопка «Мои». Поездки фильтруются по менеджеру заявки, задачи — по исполнителю. В карточке поездки показываются задачи выбранного исполнителя.
- Создание задачи из поездки подставляет заявку и ответственного. Редактирование и выполнение используют существующие TaskModal, TaskList и API канбана; отдельные копии задач не создаются. Выполненные и отмененные исключаются из открытых.
- Обновление при событиях задач, возвращении на вкладку и каждые 30 секунд. Ошибка загрузки показывает сообщение и сохраняет последнюю успешную выборку с предупреждением.

## Источники дат и поездок

Добавлено необязательное поле `Lead.return_date` и редактор «Дата прилета / возвращения» в карточке заявки. Сюда вводится фактическая дата возвращения по билетам с учетом ночного перелета.

Приоритет вылета: дата CRM, затем начало тура U-ON. Приоритет возвращения: поле CRM, затем окончание тура U-ON, затем вылет + число ночей. Последние два варианта явно отмечены как требующие уточнения или ориентировочные; они не выдаются за подтвержденный прилет. Возвращение раньше вылета исключается из списка возвращений и попадает в проверку дат.

В поездки входят локальные заявки от бронирования до успешного закрытия: booked, prepaid, waiting_payment, paid, departure, check_in, returned, closed_won. Успешно закрытые будущие поездки сохраняются. Ранние этапы и отказы не попадают в списки.

Локальные заявки с одним `uon_request_id` объединяются в одну поездку с общим набором связанных задач. Для отображения выбирается первая по ID подходящая заявка. Пространства ID заявки U-ON и обращения U-ON не смешиваются. Отдельные неархивные заявки U-ON дополняют выборку, если у них нет локальной связи и явного статуса отказа/отмены. Неизвестные пользовательские статусы U-ON сохраняются. Менеджер U-ON определяется только по уникальному точному совпадению имени или логина активного сотрудника.

API `GET /api/crm/operations/` принимает `days=1|7|30`, необязательные `start=YYYY-MM-DD` и `assignee=ID`. Требует авторизации, возвращает `Cache-Control: private, no-store`. GET ничего не создает и не меняет. Новые автозадачи и сообщения туристам не добавлены.

## Проверка

- 49 тестов Django: новая выборка поездок, авторизация, источники и границы дат, дедупликация, связи задач, фильтрация, сохранение даты возвращения, существующая синхронизация задач и закрытые задачи.
- 12 тестов frontend: объединение срочных задач, фильтры, параметры API и существующие проверки доски и формы задачи.
- Production build Next.js с TypeScript.
- Браузерная проверка на синтетических данных: фильтры периода и менеджера, выполнение задачи с обновлением счетчиков, создание связанной задачи с ответственным поездки, отображение предупреждений об источниках дат. Реальные записи CRM при проверке не изменялись.

`makemigrations --check --dry-run` выявляет существующие расхождения старых названий индексов Contact/TourOperatorExchangeRate и verbose_name поля туроператора. Они не относятся к этой странице и в изменение не включены. Новое поле соответствует миграции 0028; миграция применяется в тестовой БД.

## Обновление сервера

Перед запуском нового backend обязательна миграция `leads.0028_lead_return_date` (nullable-поле, без заполнения старых данных):

```bash
cd /opt/sletat &&
git pull --ff-only origin master &&
docker compose -f docker-compose.prod.yml build backend frontend &&
docker compose -f docker-compose.prod.yml run --rm --no-deps backend python manage.py migrate --noinput &&
docker compose -f docker-compose.prod.yml up -d --no-deps backend frontend
```

После обновления открыть `/crm/operations` под учетной записью сотрудника. При откате к предыдущему коду необязательное поле можно оставить в БД.
