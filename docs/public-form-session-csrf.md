# Публичные формы и сессия CRM — 31.10.2026

Симптом: POST /api/gift-certificates/ возвращает 403 CSRF token missing у посетителя с действующей CRM-сессией. AllowAny не отменяет SessionAuthentication: аутентификация выполняется до проверки разрешений и требует CSRF для cookie-сессии. Обычная публичная форма /api/leads/ наследовала ту же проблему.

LeadCreateView явно использует authentication_classes = []; GiftCertificateCreateView наследует это поведение. Публичные методы принимают данные без использования полномочий сотрудника, как и прежде для анонимного посетителя. Внутренние CRM-методы, middleware, SessionAuthentication по умолчанию, лимит lead_create, валидация и согласия не изменены. Глобальных csrf_exempt и отключения защиты CRM нет.

Регрессия: Django Client(enforce_csrf_checks=True) с настоящей сессией, CSRF-cookie и без CSRF-header. Проверяется приём сертификата, приём обычной заявки, отказ без обязательного согласия и отказ при POST во внутреннюю CRM без CSRF. До исправления 3 из 4 проверок падали из-за преждевременного 403; после исправления 24 теста gift/site consents прошли. Очереди и интеграции замоканы; тесты используют временную SQLite, реальные заявки не создаются.

В production нужен rebuild/restart backend. Frontend и миграции не нужны. До установки можно отправить форму из приватного окна без CRM-сессии (это обходной способ, не установленное исправление).
