# Согласия в публичных заявках на подбор путешествия

После уточнения владельца у заявки два независимых пункта, оба изначально сняты:

1. Обработка персональных данных для подбора путешествия и ответа по заявке — обязательный. Обратная связь является целью этой обработки; отдельной третьей галочки в общей форме нет.
2. Информационные и рекламные рассылки — необязательный. Отказ не мешает отправке заявки.

Тексты и источники:
- `/consents/personal-data`: адаптация заполненного согласия на сертификат под подбор тура, маршрута и экскурсий. Сохранены реквизиты, контакты, действия с данными, сроки и порядок отзыва. Обновлены только цель, состав данных и пояснение о связи по заявке.
- `/consents/marketing`: заполненный текст владельца взят за основу. Его содержание, каналы, реквизиты и порядок отказа сохранены; пояснение об изначальном состоянии отметки адаптировано к форме подбора тура, где обе отметки сняты. Документы и форма сертификатов не менялись.

Документы подбора хранятся одинаково в `frontend/src/content/leadConsents.json` и `backend/leads/lead_consents.json`; оба документа взяты за основу из заполненных `giftConsents.json` / `gift_consents.json`. Версия `2026-10-26.tour.1` относится к документам формы подбора; исходная версия владельца указана в `based_on_gift_version`. Сервер отклоняет устаревшую версию, чтобы посетитель прочитал актуальные условия.

## Передача и хранение

Общая LeadForm, чат и оба горнолыжных теста используют LeadConsentFields и передают в `POST /api/leads/`: обязательный `consent=true`, `consent_marketing` (по умолчанию false) и `consent_version`. Внутреннее создание заявки в CRM и отдельный API сертификатов сохранены.

Миграция `leads.0022_lead_site_application_consents` добавляет JSON `Lead.site_application_consents`. Сервер фиксирует время, оператора, ИНН, версию, выбор, адрес и полный текст каждого документа. Полученный от клиента снимок не используется. Старые заявки получают пустой JSON; согласия задним числом не создаются. Дата существующего персонального согласия и снимки заявок на сертификаты не изменяются.

Снимок доступен в CRM: «Согласия из формы сайта» и API деталей заявки. Админка выводит его только для чтения, обычное редактирование заявки не меняет доказательство согласия.

Для нового контакта из публичной заявки маркетинговые флаги включаются только при выборе рассылок. Email-разрешение и подписчик создаются при наличии email. Если email не указан, выбранное согласие сохраняется, доступность мессенджеров отмечается по номеру телефона. При невыбранных рассылках новый подписчик не создаётся, прежняя отписка не меняется. Отсутствие галочки в новой заявке не служит отзывом согласий из других самостоятельных обращений — для отзыва действуют способы из документа.

Создание заявки, контакта и выбранной email-подписки выполняется атомарно; ошибка не оставляет частично созданные записи. Доработка не рассылает рекламные сообщения.

## Проверки

- 12 новых серверных тестов, 8 существующих тестов сертификатов и проверка публичной постановки первой задачи: 21 из 21 прошли.
- Регрессия leads/kanban/integrations/telegrambot: 383 проверки, 380 прошли; три прежних несвязанных сбоя сохранены (сопоставление менеджера по имени и два старых ожидания запрета назначения заявок менеджерами).
- 3 теста настоящего React-компонента согласий и 5 тестов статистики страниц прошли.
- TypeScript, ESLint изменённых JS/TS/TSX, production Next.js build и проверка содержимого построенных юридических страниц.
- Реальный переход миграции 0021 → 0022 на временной SQLite: старый снимок сертификата и дата согласия сохранены, новое поле пустое.
- Браузерная проверка настоящих компонентов с тестовым API: обязательный пункт блокирует отправку; без рассылок отправляется false, с ними true; выбранная сборка сохранена. На 390 и 320 px нет горизонтального переполнения; мобильный диалог помещается в экран и поддерживает прокрутку.

В боевую CRM тестовые заявки не отправлялись. Для установки нужны обновление frontend и backend и миграция 0022, затем перезапуск процессов. Установка на production из этой среды не выполнена.
