# Закрытые задачи и успешные сделки — 25.10.2026

## Реализованное поведение

Рабочие канбан и список показывают только открытые задачи. Справа находится кнопка «Показать закрытые задачи» со счётчиком. Она открывает раздел «Закрыто»: выполненные и отменённые задачи, поиск и фильтр ответственного, сортировка по фактическому времени закрытия. Для старой записи без известной даты используется updated_at только как порядок сортировки; дата закрытия не выдумывается. Задачу можно открыть, изменить или возобновить. На карточке канбана добавлена кнопка быстрого выполнения. Архив прежних импортов U-ON в этот раздел не возвращается.

Статусы done/cancelled и их собственные колонки сохраняются в модели и API, поэтому прежние ссылки, бот и напоминания продолжают работать. UI объединяет их в раздел «Закрыто». В работающем канбане остаются Новая, В работе, Ждём клиента, Отложено.

Три типа задач: «Работа по заявке», «Выдача документов», «Связь через полгода». Тип выбирается в форме; у автоматического следующего контакта и контакта после сделки тип и связь фиксированы. Два исключения — разовые задачи, без ежедневного повторения.

При переходе локальной заявки в `closed_won` / «Успешная» закрываются открытые связанные задачи, кроме двух исключений. Учитываются задачи локальной заявки и её U-ON заявки/обращения, включая прямые ссылки без локального FK. Записываются закрытие и причина «Сделка успешна». Ежедневная задача закрывается без создания преемника. Следующий контакт закрывается и очищает соответствующую контактную дату. Прежние выполненные/отменённые задачи и архив не переписываются. Обычные новые задачи, которые сотрудник намеренно создаст после закрытия, разрешены.

Для перехода заявки U-ON применяется то же правило. Используются только точные названия после нормализации регистра и пробелов: «Успешная», «Закрыта (успех)», `closed_won`. Числовые status_id не угадываются; «Неуспешная», «Завершена», is_archive и неизвестные пользовательские названия успехом не считаются. Локальный статус сделки при этом не заменяется статусом зеркала U-ON.

Закрытие сделки и связанное изменение задач выполняются в одной транзакции. Порядок блокировок сохраняется: сначала запись сделки, затем задачи. Проверен откат состояния при ошибке; PostgreSQL-гонки в этой среде не воспроизводились.

## Два сохраняемых сценария

**Выдача документов.** Существующий ежедневный проход за 5 дней до вылета сохранён. Новая задача получает явный тип, стабильный ключ и срок текущего прохода, чтобы включались обычные напоминания по сроку. Повторный проход после выполнения, отмены, архивирования или переименования не создаёт новую копию; также учитывается уже существующая задача по связанной локальной заявке. Сценарий пока опирается на даты заявок U-ON, а не на отдельный планировщик всех местных туров.

**Контакт через полгода.** На новом успешном закрытии создаётся одна отложенная задача. Срок — 6 календарных месяцев от возвращения, в 10:00 МСК: сначала date_end U-ON, затем локальные departure_date + nights, иначе дата успешного закрытия. Последний день месяца корректируется до существующего дня целевого месяца. Ответственный — менеджер локальной заявки, иначе найденный менеджер U-ON; при отсутствии совпадения задача остаётся неназначенной. Срочность не маркируется как «Срочно» только из-за привязки к заявке.

Существующий контакт этого типа используется вместо создания дубля, его срок/ответственный/состояние сохраняются. При отсутствии технического ключа он получает ключ и происхождение автоматического контакта. Завершённая или архивная задача тоже не создаётся повторно. Повторное сохранение и повторное успешное закрытие не размножают контакты. При первом обнаружении старой успешной заявки U-ON новый полугодовой контакт не создаётся.

Запоздавшая фоновая задача первого контакта и ежедневная проверка «без движения» не восстанавливают работу по локально закрытой или успешной U-ON заявке. Остальные этапные автозадачи ниже являются предложением, а не включёнными правилами.

## Существующие данные

Миграция `kanban.0011` распознаёт старые названия выдачи/передачи документов и связи через полгода, сохраняет им явный тип, отключает ежедневное повторение у этих разовых исключений. Остальные активные задачи уже успешных сделок завершаются, включая прямые связи U-ON. ID, сроки, ответственные, архив и файлы сохраняются. После закрытия восстанавливается порядок активных колонок. Новые исторические контакты и ежедневные копии не создаются.

Если старая задача исключения названа нестандартно и не содержит узнаваемого назначения, после обновления ей можно выбрать тип в форме и возобновить из раздела «Закрыто»; автозакрытие обратимо. Миграция не удаляет записи.

Установка: пересобрать backend/frontend/celery_worker/celery_beat/telegram_bot; остановить прежние backend/worker/beat/bot; выполнить migrate новым backend-образом; поднять все сервисы. Подробные команды приведены в `unified-crm-tasks.md`.

## Предлагаемое следующее развитие — пока не включено

| Событие | Автозадача и защита от дублей |
| --- | --- |
| Новая заявка | Один первый контакт, срок в течение 30 минут рабочего времени; назначение на сотрудника по графику 3×3. Существующая назначенная связь имеет приоритет. |
| Подборка отправлена | Один повторный контакт на следующий рабочий день, если менеджер не назначил свою дату. После ответа задача заменяется следующим действием. |
| Предоплата | Контроль остатка по указанному дедлайну, без создания ежедневных одинаковых задач; предупреждение заранее. |
| Возвращение | Запросить обратную связь на этапе «Прилет» до закрытия в «Успешная», чтобы не добавлять третье исключение без отдельного решения. |
| Просрочка | Отдельный вид руководителя: без ответственного, просроченные, ожидающие клиента; приоритет определяется сроком, а не только типом записи. |

Базовое правило для новых сценариев: одна открытая задача одного назначения на сделку; пересчёт существующего срока вместо новой копии; отмена неактуальной автоматики при смене этапа. Документы и полугодовой контакт продолжают жить после успешного закрытия. Сроки реакции, выходные, часовые пояса поездки, перенос тура и причины остановки цепочки требуется явно согласовать перед включением новых сценариев.

## Проверка

Серверные тесты покрывают закрытие локальной/U-ON сделки, оба исключения после переименования, архив, связи, отсутствие повторов, календарные границы полугода, первичный импорт истории, откат транзакции, ручное закрытие/возобновление, API-фильтры и запоздавшие автозадачи. Node-тесты проверяют непересечение открытого/закрытого списка и порядок закрытия, прежний перенос карточек, сроки формы и service worker. TypeScript, ESLint изменённого интерфейса и production build проходят.

Переход реальной схемы 0010 → 0011 проверен в отдельной SQLite-базе на 9 старых записях: 4 обычные задачи закрылись, 2 исключения остались открыты, архив/вложение/сроки сохранились, новых повторов/исторических контактов нет. Браузерная проверка компонентов с синтетическим API покрыла быстрое выполнение, счётчик и кнопку справа, раздел «Закрыто» и возобновление. Production не обновлялся; доставка настоящих уведомлений и PostgreSQL-конкуренция здесь не проверены.

В общем наборе остаются три прежних сбоя: поиск менеджера только по имени и два устаревших ожидания ограничения назначения менеджерами. Политика доступа в этой доработке не меняется.
