# Статистика статей в CRM

В CRM → «Статьи» добавлен блок с динамикой просмотров и средним временем просмотра. Периоды: 7/30/90 дней или свои даты (1–366 дней), выбор одной статьи или всех. Есть сравнение с предыдущим периодом той же длины, графики просмотров/времени, таблица по статьям и таблица дневных значений. Обновление — при открытии, смене фильтров и кнопкой «Обновить». Доступ наследует существующую политику раздела: аутентифицированные сотрудники CRM.

## Значения показателей

- **Просмотр** — открытие опубликованной статьи в браузере, когда вкладка видима и окно активно. Новая загрузка страницы — новый просмотр; возврат из back-forward cache — новое открытие. Это не число уникальных людей.
- **Время просмотра** — накопленное время, пока документ видим и окно имеет фокус. Паузы при уходе на другую вкладку или в другое окно не включаются. Активность мыши и чтение конкретного абзаца не определяются; это измерение времени страницы, а не доказательство прочтения.
- **Среднее время** — сумма накопленного времени / число открытий с полученным измерением длительности. Общая средняя взвешивается по просмотрам, а не усредняется из средних по статьям. Отдельно показано, для скольких просмотров получено время.
- Прочерк — измерений длительности нет. Нулевое время — получено измерение короткого просмотра. На графике времени пропуски не соединяются.
- Даты и границы суток — `Europe/Moscow`; конец выбранного дня включён. Просмотр и его суммарное время относятся к дню начала сессии, даже если она пересекла полночь. Предыдущий период содержит столько же календарных дней; текущий день может быть неполным. При нулевой базе и новых просмотрах показывается «Новые просмотры», без выдуманного бесконечного процента.

## Исторические данные

Прежний `Article.views` сохраняется. Миграция не распределяет старые значения по дням и не создаёт фиктивную длительность. Новые события увеличивают общий счётчик по одному разу, а дневная история и время доступны только с начала нового сбора. API чтения статьи больше не увеличивает счётчик: служебные запросы Next.js, метаданные и загрузка списка не равны открытию страницы. Поэтому метод подсчёта новых просмотров отличается от прежнего счётчика API-запросов. В интерфейсе исторический итог отделён от показателей периода.

## Сбор

Новая модель `ArticleReadSession` и миграция `0031_article_read_sessions` (после 0030). Один случайный UUID на открытие, FK статьи, серверные отметки начала/последнего события, накопленные миллисекунды, признак полученного измерения. Нет записи имени, контактов, идентификатора посетителя, IP или User-Agent в таблицу сессий; cookies/localStorage для отслеживания посетителя не создаются.

Клиентский компонент `ArticleReadTracker` подключён к общей странице `/blog/[slug]`, включая статью о пляжах Пхукета. Он отправляет старт, накопленное время каждые 15 секунд активного просмотра и итог при скрытии/закрытии/переходе. При завершении используется sendBeacon, затем keepalive-fetch как запасной вариант. Ошибки сбора не мешают читать статью. При dev-перемонтировании React ID сохраняется; на смене статьи создаётся новый.

`POST /api/articles/<slug>/read-event/` принимает JSON `{view_id, active_ms, kind: start|progress|end}`. Endpoint анонимный, не использует сессию авторизации и принимает beacon даже при существующих cookies без CSRF-токена. Это только ограниченный endpoint записи метрик; прав CRM он не предоставляет. Учитывает опубликованные статьи с наступившей датой, пропускает известные crawler User-Agent, ограничен 120 запросами в минуту на IP стандартным throttle-кешем DRF.

UUID — первичный ключ. Создание/увеличение общего счётчика выполняются в транзакции; обновление сессии блокируется select_for_update. Повторы и пришедшие не по порядку пакеты не уменьшают время и не увеличивают просмотры. Один UUID нельзя перенести между статьями. Максимум на сессию — 2 часа активного времени; заявленное время дополнительно ограничено серверным возрастом сессии с допуском 3 секунды.

Измерение ориентировочное: JavaScript, сеть, блокировщики, завершение браузера и ограничения фоновой работы могут помешать доставке событий. Время по потерянным событиям не восстанавливается. При утерянном стартовом запросе последующие данные могут быть ограничены серверным возрастом сессии. Это собственная статистика сайта, не импорт и не точное повторение метрик Яндекс Метрики. Существующий счётчик Метрики сайта не изменяется.

## Отчёт

`GET /api/crm/articles/analytics/?start=YYYY-MM-DD&end=YYYY-MM-DD&article_id=ID` — только с авторизацией CRM. Параметр article_id необязателен. Ответ содержит период и предыдущий период, дату первого события, общие показатели, дневные строки с заполненными нулями, показатели всех статей для списка выбора. Агрегации выполняются в БД; ответ и клиентский запрос не кешируются.

Существующие CRUD и формы статей сохраняются. Таблица редактирования остаётся ниже нового блока; её счётчик явно подписан как общий за всё время. Удаление статьи удаляет её сессии по существующей каскадной связи.

## Проверки

- 37 тестов приложения articles на Django 6.0.9 / DRF 3.15.2: CRUD, права, новая семантика счётчика, повторы/порядок событий, сохранение исторического итога, проверки UUID/времени/статуса публикации, CSRF для анонимного beacon, агрегаты, взвешенная средняя, отсутствие/ноль измерений, московская полночь, границы/фильтры периода. Тесты API запускались в изолированной конфигурации accounts/articles на SQLite без seed-данных.
- Отдельно выполнена полная реальная цепочка миграций до 0031 на SQLite: сохранение всех существующих счётчиков, текстов, статусов и дат; отсутствие разницы между моделями и миграциями. PostgreSQL-нагрузочный тест не выполнялся.
- Production-сборка Next.js 16.2.10/Turbopack, TypeScript и ESLint изменённых файлов.
- Реальный standalone frontend и Django API с тестовой авторизацией/синтетическими данными: фильтры, график, пустое состояние и восстановление после 503 при 1440 и 1024 px. Проверен трекер с видимостью/фокусом, heartbeat, итоговым событием и одним счётчиком на повторные пакеты. Существующие внешние картинки и Метрика в браузерном тесте блокировались; боевые данные не затрагивались.
- Автономный предпросмотр нового блока на 1440/390 px: демонстрационные данные явно подписаны, фильтры и график работают без обращения к CRM и внешних запросов.

## Установка

После согласования и включения изменений в master необходимо обновить **backend и frontend**, применить миграции новой backend-версией и запустить обновлённые сервисы. До миграции у нового API нет таблицы сбора; общий счётчик по старым данным при установке сохраняется. Реальные дневные показатели и время начнут поступать после открытия статей посетителями. Задним числом заполнить их нельзя.
