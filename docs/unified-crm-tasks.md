# Единые задачи CRM — 24.10.2026

Обновление 25.10.2026: выполненные/отменённые задачи вынесены из рабочей доски в «Закрыто»; успешная сделка завершает обычные связанные задачи. Исключения и новые правила — в [closed-tasks-and-successful-deals.md](closed-tasks-and-successful-deals.md).

Статус и колонка больше не являются независимыми полями. Во всех интерфейсах действуют шесть состояний: Новая, В работе, Ждём клиента, Отложено, Выполнено, Отменено. Стабильный `KanbanColumn.status` определяет колонку; её положение и название не используются для определения завершения. Продажный этап связанной заявки показывается отдельно с подписью «Этап заявки/обращения».

## Работа сотрудника

В пункте «Задачи» доступны канбан и список с теми же карточками. Статус меняется перетаскиванием, в форме и селектором списка. Перетаскивание доступно с поиском и фильтрами ответственного/даты; скрытые фильтром задачи сохраняют своё место. В сортировке по сроку/приоритету можно менять колонку, ручной порядок внутри колонки задаётся в режиме «Порядок на доске». Отмена перетаскивания восстанавливает прежнее состояние; серверная ошибка видна пользователю.

В карточках локальных заявок, обращений и заявок U-ON находится блок задач: создать, открыть, назначить ответственного, перенести срок, выполнить, отменить или возобновить. Локальная карточка включает также задачи, привязанные непосредственно к её U-ON ID. Завершённые и отменённые задачи находятся в раскрываемом списке. Из задачи можно перейти к связанной записи CRM.

После изменения данные обновляются в текущей странице и соседних вкладках. При возврате на страницу выполняется обновление; видимая страница также перечитывает данные каждые 30 секунд для изменений коллег, фоновых процессов и бота. Это обновление через запросы, без WebSocket. Формы и перенос передают `expected_updated_at`: устаревшее изменение возвращает 409 и не перезаписывает новую версию задачи.

## Жизненный цикл

- Изменение статуса, перетаскивание, ORM-сохранение и Django admin используют общий сервис `Task.save()` → `save_task`. Пакетные изменения `QuerySet.update` обходят этот сервис: не применять их для статуса/колонки вне миграций.
- «Отложено» при входе с неизменённым сроком переносит его на 3 дня один раз. Если сотрудник явно выбрал другой срок, сохраняется выбранная дата. Повторное сохранение/перетаскивание в ту же колонку не сдвигает срок снова. При неизменённом поле даты форма не обрезает секунды/микросекунды исходного значения.
- «Выполнено» и «Отменено» исключаются из push, открытых задач бота, сводок и просрочек. Архив тоже исключён. Просроченный срок — раньше текущего момента, включая сегодняшний день; фильтры дней используют Europe/Moscow.
- Выполнение повторяющейся задачи создаёт одну следующую задачу с `recurrence_parent`; повторное выполнение после возобновления не дублирует преемника, даже если он уже архивирован. Отмена не создаёт повтор. Следующий срок — на день позже предыдущего, с продвижением в будущее для просроченной серии. Без исходного срока новая задача тоже остаётся без срока.
- Следующий контакт создаётся с каналом связи из заявки; срок и ответственный синхронизируются в обе стороны. Завершение, отмена, архивирование или удаление очищают соответствующую контактную дату и пересчитывают автоматические метки. Изменение срока переносит контакт; возобновление восстанавливает его дату. Контактную задачу нельзя перенести в другую заявку или сделать ежедневной. Для возобновления контакта по закрытой заявке сначала открывается сама заявка.
- Этап продажи не скрывает обычные задачи: их собственные статус и архив определяют видимость. Права сотрудников не менялись; доска общая, «Мои задачи» — фильтр.

## Старые данные и установка

Миграция `kanban.0010_unified_task_states` сохраняет ID задач, связи, сроки, ответственных, вложения, происхождение и архив. Переиспользуются узнаваемые старые колонки, создаются недостающие состояния. Прочие старые колонки остаются неактивными. В активных колонках восстанавливается плотный порядок без промежутков от архивных задач.

Правило разрешения старого конфликта: явный done/cancelled сохраняется; иначе прежняя колонка завершения имеет приоритет; затем сохраняется иной явно заданный статус; для new используется узнаваемая колонка, иначе new. Миграция не переносит сроки отложенных задач и не создаёт копии повторяющихся задач. Соответствующая контактная дата завершённой контактной задачи очищается. Выводится число обработанных записей.

Сборка и миграция выполняются всеми сервисами, работающими с задачами:

```bash
cd /opt/sletat &&
git pull --ff-only origin master &&
docker compose -f docker-compose.prod.yml build backend frontend celery_worker celery_beat telegram_bot &&
docker compose -f docker-compose.prod.yml stop backend celery_worker celery_beat telegram_bot &&
docker compose -f docker-compose.prod.yml run --rm --no-deps backend python manage.py migrate --noinput &&
docker compose -f docker-compose.prod.yml up -d --no-deps backend frontend celery_worker celery_beat telegram_bot
```

Реальная цепочка миграций 0009 → 0010 проверена на отдельной SQLite-базе с девятью противоречивыми старыми записями. Все записи и вложение сохранены, активные позиции упорядочены, архив сохранён, лишних повторов нет. `makemigrations kanban --check --dry-run` не показывает отличий.

Браузерная проверка реальных компонентов с синтетическим API: выполнение из карточки заявки обновляет доску, перенос с «Мои задачи» отражается в связанном списке, редактирование/отмена и создание связанной задачи показывают один статус в обоих представлениях. Это локальная проверка интерфейса, не production. PostgreSQL-гонки, фактическое применение production-миграции и доставка реального push в этой среде не проверены.

Общий прогон серверных тестов сохраняет три прежних сбоя, подтверждённых до этой доработки: поиск менеджера только по имени и два устаревших ожидания запрета назначения заявок менеджером. Их исправление и изменение действующей политики доступа в этот объём не входят.
